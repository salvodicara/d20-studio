# Market census — Foundry VTT cluster (core, dnd5e system, community modules)

Access date: **2026-09-23**. Author session: market-census subagent (interview-01). This file
extends [reference-audits/foundry.md](../../../docs/interview/reference-audits/foundry.md) (R182,
30 families). It does not replace it. That audit works at family level. This census
works at the level of a single capability and UX pattern: where the command lives, how it is
operated, what feedback it gives, how it is corrected, and who may use it.

## Scope, versions and access limits

- **Layers.** Every row is labelled **Core**, **dnd5e** (the official system) or **Module**
  (third-party). A module capability is never attributed to core. Where core later absorbed
  a module's function, the row says so.
- **Current versions, not the ones in the brief.** The brief names Foundry v12/v13 and dnd5e 4.x/5.x.
  On the access date the current versions were core **V14** (stable 14.359 on 2026-04-01; the
  Tiles KB page reports 14.368 on 2026-09-22) and dnd5e **6.0.x** (6.0.0 on 2026-09-10, 6.0.5 on
  2026-09-22, V14 only). Each row records the version that introduced or documents the capability.
  Capabilities from v12/v13 and dnd5e 3.x–5.x are included when they are still current.
- **Evidence kinds.** *Official docs* means the Foundry KB or the dnd5e GitHub wiki. *Release notes*
  means foundryvtt.com/releases or dnd5e GitHub releases. *Store page* means the official
  foundryvtt.com/packages listing, which is written by each author. *Community* means forum,
  blog or wiki opinion, used only as a demand or risk signal.
- **How the sources were read.** All sources were read through a web-fetch summariser. No account,
  installation, runtime session or human playtest took place. KB pages often carry no version.
  In that case the row gives the date of the screenshots or header the page shows, and marks
  it. The GitHub release pages showed ambiguous years. Years marked "inferred" come from the
  required core version (for example, V13-only implies 2025 or later).
- **Store-page limits.** A store-page "last updated" value is relative to 2026-09-23 and is given
  approximately. Store descriptions are the author's own claims. Where the fetched summary looked
  like it was echoing the prompt, only features I could corroborate elsewhere are kept. This
  applies to the Argon feature list.
- **Coverage column.** An **F-0nn** code means a family exists in
  [FEATURES](../../../docs/interview/FEATURES.md) and the pattern is at least named there or in a
  flow document. **PARTIAL F-0nn** means the family exists, but a keyword check of
  `docs/interview/` did not find this sub-pattern specified. **NEW** means no family or anchor was
  found. GAP-nn refers to
  [REFERENCE_COVERAGE](../../../docs/interview/REFERENCE_COVERAGE.md). The keyword check is
  a grep, not a re-read of every contract page. Treat PARTIAL and NEW as work items to verify,
  not as proven absences.
- **Standing exclusions.** In-app voice/video calls (F-017) and in-app music (F-030) remain out
  of scope. Their rows are kept only for interface-feedback lessons. 3D environments are excluded;
  2D levels and elevation are not.
- **Rules content.** No rules text is reproduced. Capabilities are described as UX facts only.

## Pattern notes — the UX patterns most worth copying

1. **The chat card is where consequences are resolved** (dnd5e 3.1→6.0, best in 6.0). Using an
   item posts one card with the activity's facts and next-step buttons (attack → damage → save →
   apply effect). Targets are grouped with context menus. It works because every consequence has
   one visible, auditable place with its correction controls, instead of silent state changes.
   *Conflict:* Midi-QOL auto-resolves the whole chain, the core system keeps the steps manual,
   and Effective Tray sits between them. d20 Studio needs an explicit automation-level setting
   per campaign (FVT-138/141/143).
2. **Preview damage before applying it, with per-target overrides** (dnd5e 3.1). Each target
   shows the computed result, chips for resistance, immunity and vulnerability that the DM can
   toggle, and multiplier buttons. It lets the DM exercise judgement *before* HP changes, which
   removes most undo needs. This is the best-in-class pattern here (FVT-139).
3. **Drag-to-move with a live, speed-coloured ruler** (core V13 + dnd5e 5.1). Waypoints on
   Ctrl+click, right-click removes one waypoint, Esc cancels, the wheel changes elevation, Tab
   cycles movement type, and the ruler is coloured green/yellow/red for speed/Dash/beyond. It is
   direct manipulation with the rules cost shown *during* the gesture (FVT-110/111). BG3 is the
   parallel reference; Foundry's waypoint grammar is the most complete VTT version.
4. **Right-click token HUD for in-place state edits** (core). HP bars that accept typed values,
   a condition palette, elevation, hide, target and combat toggle all sit around the token. Monk's
   Little Details shows the fixes users ask for: named, alphabetised conditions and "clear all"
   (FVT-119/120).
5. **Edit mode vs Play mode on the sheet** (dnd5e 3.0). Separate building from playing: effective
   values and quick actions in Play, base values and construction controls in Edit. This removes
   the "why is my number different" confusion that effects cause (FVT-008).
6. **An advancement wizard fired by a drop, with modify, rollback and nested choices**
   (dnd5e 3.0–5.3). Dropping a class starts a stepwise dialog. Level-down offers to remove what
   was granted. Past levels can be re-chosen. Subclass is picked inside the flow. The **locked
   compendium picker** keeps each choice filtered to its context (FVT-011–014).
7. **One item, several activities, with a usage dialog** (dnd5e 4.0). One click asks which
   activity to use; Shift+click takes the primary one. The dialog confirms consumption, upcast and
   template placement. The explicit confirmation of *what will be spent* is the pattern to keep
   (FVT-017/018).
8. **DM roll requests as clickable cards** (dnd5e enrichers `request`, rest requests in 5.1,
   TokenBar group saves). The DM sets roll, DC and mode. Players get a button. A progress or
   summary card tallies results. This keeps DM authority and player agency (they roll, with
   physical or digital dice) (FVT-146–148).
9. **Physical dice through per-die fulfilment** (core V12+). Each die type can be digital, manual
   entry or an external or Bluetooth provider, set per user. This matches d20 Studio's
   physical+digital baseline without separate code paths for "manual rolls" (FVT-153). Dice So
   Nice shows that animated shared dice are a presentation layer on the same roll (FVT-155).
10. **Roll visibility modes, with reveal later** (core). Four explicit modes next to the chat
    input, plus a context-menu reveal afterwards. The DM decides privacy per roll; nothing needs a
    second roll to go public (FVT-150).
11. **Ownership levels per document, inherited from folders** (core). None / Limited / Observer /
    Owner, a default for all players with per-user overrides, set from the context menu on any
    document or folder. Simple enough for DMs, granular enough for handouts. *Conflict:* in
    Foundry the GM always sees everything. d20 Studio keeps "Only me" private (audit #2), so copy
    the levels, not the GM-omniscience (FVT-048).
12. **Journal secrets with reveal, and "show to players"** (core). Secret blocks inside a page,
    a reveal toggle per block, and Show Players to all or selected users. Monk's Enhanced Journal
    adds typed pages (Person, Place, Quest, Shop, Loot) and browser-like tabs, back/forward and
    bookmarks. That is what DMs reach for in prep (FVT-054/057/162).
13. **Runnable text: enrichers and embeds** (dnd5e). Adventure text holds clickable checks, saves,
    damage, awards and stat blocks, so prep material *is* the control surface at the table
    (FVT-146/175/176). Pairs with map-location pages that number pins (FVT-088).
14. **Event → action behaviours on map regions** (core Regions + Monk's Active Tile Triggers +
    dnd5e 6.0 AoE regions). Region shape, events (enter, exit, turn start…), an ordered list of
    actions, an optional probability and an optional one-shot. This is the verified pattern for
    traps, teleports, hazards and persistent AoE. *Conflict:* core offers raw "execute script",
    while Monk's offers a curated action list. The curated list is safer for a non-programmer DM
    (FVT-082/084/117).
15. **Combat tracker with hidden and defeated combatants, grouping and turn alerts** (core +
    dnd5e 4.3/6.0 + Monk's Combat Details). Right-click a combatant for hidden/defeated/reroll.
    NPCs of one kind grouped. A marker under the active token. "Your turn is next" alerts for
    players (FVT-127–133). The carousel and Argon HUDs show demand for a BG3-style horizontal and
    action-bar presentation (FVT-134/135).
16. **Undo at the right granularity** (core Ctrl+Z for canvas; Damage Log for HP; Not Your
    Turn's "undo movement"; Clear Movement Histories). Foundry has no global consequence rollback,
    and turning the tracker back does not revert outcomes. Community modules add *targeted* undo
    through a log. Copy the log-based, per-consequence correction rather than a global undo
    (FVT-112/114/144/201).
17. **Command palette** (Quick Insert, Ctrl+Space). Context-filtered search that also inserts,
    runs commands and calculates. It suits the owner's command-findability goal and F-062
    (FVT-187).
18. **In-person display as a user role** (Monk's Common Display + Lock View). A dedicated
    "display" participant without UI, following the GM view or tokens, with the grid scaled to the
    physical screen (FVT-163/164).
19. **Calendar HUD that drives rules** (dnd5e 5.2/6.0 + Calendaria). The GM advances time, and
    dawn/dusk recoveries and bastion orders resolve from it. Notes carry Visible/Hidden/Secret and
    reminders. This joins time, rest and prep into one control (FVT-060–062).
20. **Settings with explicit scope** (core). Every preference is labelled client, user or world,
    and keybinds have conflict warnings and reset. That resolves "who does this affect" before the
    change is made (FVT-188/191).

### Conflicts and cautions between products

- **Core absorbing modules:** Drag Ruler and Elevation Ruler vs the core V13 token ruler; Times Up
  vs core effect expiry (retired); Levels module vs core V14 Scene Levels (the module still claims
  extras); PopOut! vs core V14 pop-outs. Prefer the core pattern as the baseline and name the
  module extras explicitly.
- **Automation depth:** dnd5e (assisted, manual apply) vs Midi-QOL, DAE and Chris's Premades
  (full automation, heavy dependency chain). Effective Tray is incompatible with Midi-QOL. Community
  opinion warns about module conflicts and overload (FVT-207).
- **Stale but influential modules:** Perfect Vision (V10), Quick Encounters (final at V12), Simple
  Calendar (dormant), Better Rolltables (V12), Anonymous (V12), Monster Blocks (V12), Forien's
  Quest Log (V13). Their patterns are still valid references. Their current compatibility is not.
- **Privacy model:** the Foundry GM sees all documents. d20 Studio's private notes forbid copying
  that behaviour (existing decision, audit #2).
- **Paid tiers:** Epic Rolls, Mastercrafted, FXMaster+, Swipe premium and DDB Importer's monster
  import use Patreon gates. A pattern being copyable does not mean the product relies on paid
  third parties.
